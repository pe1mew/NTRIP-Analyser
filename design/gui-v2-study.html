Three constraints already in the app

The way out of Analysis is a gesture

You leave the pager by over-swiping page 0, and a nested-scroll handler reads the leftover drag. It broke once already on Android 12's stretch overscroll. Reorder or prepend a tab and the exit changes meaning.

MainActivity.kt:508

The app deliberately carries no map

No tile requests from this process, so Play data safety stays “no data collected or shared”; no OSM tile-policy exposure; no attribution to maintain. Maps are handed to an app the user already has.

MapPick.kt:11

The foreground service exists

MonitorService already owns the run, because 60 continuous seconds outlasts a backgrounded activity. Tier 2 is not building one — it is making this one survive hours.

MonitorService.kt:34

The dimension the mockups don't show

Two clocks and one continuous view

Every screen above is a finished run, which is the easy case. What the app actually is, is a machine with states — and the roadmap adds a second measurement that runs on a different clock from the first. Three things run at once, and they are not the same kind of thing:

Which means every card has four states, not one

A tab strip cannot say not yet — a tab is either there or it isn't, and an empty one is a dead end. A card has a line of text to spend on it. This is the strongest argument for the hub, and it only appears once you look at the run as a sequence rather than a result.

The fourth state is not hypothetical: tier 2 gained it in 3.5.0, after a monitored station published STABLE over 1.7 h for fourteen hours past its last observation. Whatever the navigation, the UI has to be able to show a verdict being taken back — which a card does in place, and a screenful of numbers does only if the reader happens to be looking at it.

One practical consequence for the ordering: tier 2 rides on the run that already exists. Watch mode holds the session open and MonitorService keeps it alive; tier 2 adds a reader of the same snapshots, not a second connection. That is why scheduling the foreground-service work with tier 2 rather than after it is right — the two are the same piece of work seen from either end.

The map, which is a separate decision

Hand-over is the only geographic item, and the question it asks is relative — where is the ARP with respect to me, and did it jump while I stood still. That can be answered without a basemap, which is the difference between keeping the privacy position and reopening it.

Layering: make the first item carry the rest

MainActivity.kt is 2,147 lines and already holds the shell, both screens and seven cards. Five more features added the current way make it four thousand. The alternative uses the mechanism that already exists — compile-time Features constants over free / pro source sets — and adds one contract.

Three questions decide it

Is a two-destination free app acceptable?

If yes, C becomes much stronger and I would probably switch to it — a bottom bar is what people expect, and it retires two fragile gestures. If no, D is the only option that hides paid capability without leaving a hole.

Does hand-over need streets behind the dots?

If relative geometry is enough, M2 answers it with no new dependency and no change to the data-safety declaration. If you want a basemap, that is a deliberate reopening of a decision you already documented — worth doing on purpose, not as a side effect of one feature.

Is share the plug-in point, or a one-off?

As a socket it costs more design now and makes every later feature cheaper. As a button it ships sooner and each feature edits it by hand. Its position at the top of the roadmap is what makes the first option attractive.
